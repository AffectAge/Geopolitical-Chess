# Архитектура движка пошаговой стратегии (TBS Engine Architecture)

## 1. Ядро движка и базовые системы (Core & Foundation)

### 1.1. Игровой цикл (Game Loop)

В пошаговой стратегии (Turn-Based Strategy, TBS) игровой цикл может быть событийным (Event-Driven) или гибридным, а не классическим `while(true)` с непрерывным выполнением игровой логики на частоте 60+ FPS.

**Основные требования:**
- Поддержка событийного и гибридного игрового цикла.
- Приостановка логики ходов в ожидании действий игрока.
- Разделение игрового цикла и цикла рендеринга.
- Обработка игровых событий и команд.
- Независимость частоты обновления интерфейса от логики симуляции.

### 1.2. Управление памятью и контейнеры (Memory Management & Containers)

Система управления памятью должна обеспечивать эффективное хранение и обработку игровых объектов.

**Основные компоненты:**
- Стандартные или специализированные аллокаторы памяти.
- Пулы объектов (Object Pools) для юнитов, тайлов и эффектов.
- Контейнеры для хранения игровых сущностей.
- Контроль времени жизни объектов.
- Минимизация фрагментации памяти.
- Оптимизация выделения и освобождения памяти.

### 1.3. Система событий (Event System / Event Bus)

Шина сообщений обеспечивает взаимодействие между игровой логикой, интерфейсом и другими подсистемами.

**Примеры событий:**
- `UnitMoved` — юнит переместился.
- `TurnStarted` — начался новый ход.
- `TurnEnded` — ход завершён.
- `BattleStarted` — начался бой.
- `BattleEnded` — бой завершён.
- `ResourceChanged` — изменилось количество ресурсов.
- `BuildingConstructed` — завершено строительство.

**Основные требования:**
- Слабая связанность подсистем.
- Подписка на события и отписка от них.
- Передача данных вместе с событиями.
- Предсказуемый порядок обработки событий.
- Разделение игровых событий и событий интерфейса.

### 1.4. Менеджер ресурсов (Asset Manager)

Отвечает за загрузку, хранение, кэширование и освобождение игровых ресурсов.

**Поддерживаемые ресурсы:**
- Текстуры.
- Спрайты.
- 3D-модели.
- Шрифты.
- Звуковые эффекты.
- Музыкальные файлы.
- Конфигурационные файлы (JSON, YAML, XML).

**Основные возможности:**
- Централизованная загрузка ресурсов.
- Кэширование загруженных ассетов.
- Асинхронная загрузка.
- Контроль использования памяти.
- Повторное использование ресурсов.
- Освобождение неиспользуемых ресурсов.

## 2. Специфические системы пошаговой стратегии (TBS Logic)

### 2.1. Модель карты и сетки (Grid & Map System)

Система отвечает за представление игрового мира, его геометрию и пространственные отношения.

**Поддерживаемые типы сеток:**
- Square Grid — квадратная сетка.
- Hex Grid (Pointy Top) — гексагональная сетка с острыми вершинами сверху.
- Hex Grid (Flat Top) — гексагональная сетка с плоскими сторонами сверху.
- Graph-Based Grid — свободная или граф-ориентированная структура карты.

#### Структура тайла (Tile)

Каждый тайл может содержать следующие данные:

| Параметр | Описание |
|---|---|
| Terrain Type | Тип местности |
| Elevation | Высота |
| Movement Cost | Стоимость перемещения |
| Passability | Проходимость |
| Defense Modifier | Модификатор защиты |
| Attack Modifier | Модификатор атаки |
| Resources | Природные ресурсы |
| Objects | Привязанные игровые объекты |
| Neighbors | Соседние тайлы |
| Ownership | Принадлежность территории |

### 2.2. Поиск пути и пространственная геометрия (Pathfinding & Geometry)

Система определяет маршруты перемещения юнитов и анализирует пространственные отношения между объектами.

**Основные алгоритмы:**
- A* (A-Star) — поиск оптимального пути.
- Dijkstra — поиск кратчайших путей.
- Line of Sight (LOS) — определение прямой видимости.
- Fog of War — система тумана войны.

**Учитываемые факторы:**
- Тип местности.
- Стоимость перемещения.
- Непроходимые препятствия.
- Рельеф.
- Наличие дорог.
- Занятость тайлов другими объектами.
- Особенности передвижения разных типов юнитов.

### 2.3. Менеджер ходов и состояний (Turn Manager / State Machine)

Управляет последовательностью ходов, фазами симуляции и переходами между игровыми состояниями.

#### Очередь ходов

Возможные модели:
- Последовательные ходы фракций.
- Последовательные ходы отдельных юнитов.
- Initiative System — порядок действий по инициативе.
- Simultaneous Turns — одновременное планирование действий.

#### Фазы хода

1. `TurnStart` — начало хода.
2. `ProductionPhase` — производство.
3. `UnitActionPhase` — действия юнитов.
4. `CombatPhase` — обработка боёв.
5. `AIPhase` — обработка действий искусственного интеллекта.
6. `TurnEnd` — завершение хода.

#### История и восстановление состояния

- Сохранение истории ходов.
- Снимки состояния (Snapshots).
- Журнал игровых команд.
- Undo/Redo для допустимых операций.
- Восстановление состояния после ошибок.
- Возможность воспроизведения игровой симуляции.

### 2.4. Модель данных и логика сущностей (ECS / OOP)

Архитектура должна обеспечивать чёткое разделение игровых данных, правил симуляции и визуального представления.

#### Возможные архитектурные подходы

**Entity Component System (ECS):**
- Entity — идентификатор игровой сущности.
- Component — данные сущности.
- System — логика обработки компонентов.

**Object-Oriented Programming (OOP):**
- Объекты с инкапсулированными данными и поведением.
- Наследование и композиция.
- Разделение ответственности между классами.

#### Разделение Model / View / Controller

**Model:**
- Игровые данные.
- Правила симуляции.
- Состояния сущностей.
- Экономические и боевые расчёты.

**View:**
- Рендеринг карты.
- Визуализация юнитов.
- Анимации.
- Интерфейс пользователя.

**Controller:**
- Обработка пользовательского ввода.
- Интерпретация команд.
- Передача команд игровой логике.

Такое разделение позволяет искусственному интеллекту моделировать будущие игровые состояния (Forward Modeling) без необходимости отображать их на экране.

## 3. Искусственный интеллект (AI for TBS)

### 3.1. Оценка игрового состояния (Board Evaluation / Heuristics)

Система оценки определяет стратегическую или тактическую выгодность текущего игрового положения.

**Возможные критерии оценки:**
- Военная сила.
- Экономическое развитие.
- Контроль территории.
- Доступность ресурсов.
- Технологическое развитие.
- Дипломатические отношения.
- Стратегическое положение.
- Уровень угроз.

### 3.2. Поиск и планирование действий (Search & Planning)

#### Тактический искусственный интеллект

**Основные алгоритмы:**
- Minimax — поиск оптимальных действий.
- Alpha-Beta Pruning — отсечение невыгодных ветвей.
- Heuristic Search — эвристический поиск.
- Monte Carlo Tree Search (MCTS) — поиск на основе моделирования.

**Применение:**
- Тактические сражения.
- Выбор атакующих действий.
- Оценка возможных перемещений.
- Прогнозирование действий противника.

#### Стратегический искусственный интеллект

**Основные подходы:**
- Behavior Trees — деревья поведения.
- Utility AI — выбор действий по функции полезности.
- Goal-Oriented Action Planning (GOAP) — целевое планирование.
- Rule-Based AI — система правил.

**Области применения:**
- Экономика.
- Экспансия.
- Производство.
- Военное планирование.
- Дипломатия.
- Управление ресурсами.
- Долгосрочное стратегическое развитие.

## 4. Графика, интерфейс и периферийные системы (Graphics, UI & Peripherals)

### 4.1. Графический бэкенд (Graphics Backend)

Графическая подсистема отвечает за визуализацию игрового мира.

#### Возможные технологии

**Для 2D-игр:**
- SDL2 / SDL3.
- SFML.

**Для аппаратного рендеринга:**
- OpenGL.
- Vulkan.
- DirectX.

**Вспомогательные библиотеки:**
- GLFW — создание окон и обработка ввода.
- GLAD — загрузка функций OpenGL.

**Основные задачи:**
- Рендеринг карты.
- Отрисовка юнитов и объектов.
- Управление камерой.
- Работа с текстурами.
- Анимация.
- Оптимизация графического конвейера.

### 4.2. Интерфейс игрока (UI / HUD)

Система интерфейса предоставляет игроку инструменты управления игровым миром.

**Основные компоненты:**
- Панели информации о юнитах.
- Панели территорий и провинций.
- Деревья технологий.
- Меню строительства.
- Экран дипломатии.
- Экономические панели.
- Мини-карта.
- Журнал событий.
- Главное меню.
- Окна настроек.

#### Возможные подходы к реализации

- Dear ImGui — инструменты разработки, редакторы и прототипирование.
- Собственный GUI-фреймворк.
- Интеграция сторонней UI-библиотеки.

**Основные требования:**
- Модульность.
- Повторное использование компонентов.
- Независимость интерфейса от игровой логики.
- Поддержка различных разрешений.
- Обработка пользовательских событий.

### 4.3. Система ввода (Input Handler)

Обрабатывает взаимодействие пользователя с игровым миром и интерфейсом.

**Поддерживаемые действия:**
- Выделение юнитов.
- Выделение тайлов.
- Выдача приказов перемещения.
- Выбор объектов.
- Управление камерой.
- Использование горячих клавиш.
- Взаимодействие с интерфейсом.

**Основные механизмы:**
- Mouse Input — обработка мыши.
- Keyboard Input — обработка клавиатуры.
- Raycasting — определение объектов в 3D.
- Tile Picking — определение выбранного тайла в 2D.
- Input Mapping — сопоставление ввода с игровыми действиями.

### 4.4. Аудиодвижок (Audio Engine)

Обеспечивает воспроизведение звуков и музыки.

**Возможные технологии:**
- OpenAL.
- SDL_mixer.
- FMOD.

**Основные функции:**
- Воспроизведение фоновой музыки.
- Воспроизведение звуковых эффектов.
- Управление громкостью.
- Разделение аудиоканалов.
- Пространственное позиционирование звука при необходимости.
- Загрузка и кэширование аудиоресурсов.
